# Glossary

Project-specific terminology and definitions. When something is referred to by a name that wouldn't be obvious to a newcomer, it belongs here.

- **Feature folder** — A directory under `features/<name>/` that owns a self-contained slice of UI and its colocated Zustand store. Feature folders depend on `domain/` but not on other feature folders.
- **Domain layer (`domain/`)** — Pure business-logic functions with zero external dependencies (no React, no React Native). Contains rules engines, validators, calculators, and state machines. Testable with plain Jest.
- **Zustand store** — A lightweight state management primitive (from the Zustand library). Each feature folder has its own colocated store that bridges the pure `domain/` functions to React components.
- **EPM** — (presumed) The core domain this project models. EPM rules include session state machines, SMART goal validation, skill wheel calculations, and recording policy.
- **SMART goal** — A structured goal format (Specific, Measurable, Achievable, Relevant, Time-bound). Validation logic lives in `domain/`.
- **Skill wheel** — A scoring or aggregation mechanism for skills. Calculation logic lives in `domain/`.

- **Gap Click** — A metronome exercise mode where clicks are intentionally silenced for a configurable number of beats, forcing the musician to internalize the pulse. The mute/resume schedule is computed by a pure domain function; audio playback is handled by the native metronome engine.
- **Metronome engine** — The platform-native module responsible for low-latency audio. Uses AVAudioEngine on iOS, Oboe/AAudio on Android. Receives a simple instruction list (which beats to play) from the domain layer; does not contain scheduling policy.
- **AVAudioEngine** — Apple's low-latency audio framework for iOS/macOS. Used as the iOS backend for the metronome engine.
- **Oboe/AAudio** — Google's low-latency audio libraries for Android. Oboe is a C++ wrapper that can use AAudio (API 27+) or fall back to OpenSL ES. Used as the Android backend for the metronome engine.
- **Foreground service** — An Android service that runs with a persistent notification, allowing the app to continue audio playback when backgrounded. Used to keep the metronome audible during practice sessions with the screen off or another app in the foreground.

- **EPM Journal** — The application name. A mobile-first, offline-first practice journal for musicians, built with Expo/React Native.
- **Expo Router** — Expo's file-based routing framework. Route files under `src/app/` map filesystem paths to screen components. Route files are kept thin — they re-export feature components rather than owning UI logic.
- **Practice tab** — The session runner tab. Hosts the active practice session UI (metronome, recording, timer).
- **Journal tab** — The practice journal tab. Browsing past sessions, recordings, and notes.
- **Progress tab** — The progress tracking tab. Skill wheel visualization, SMART goals, and cycle review.

- **3 Lists exercise** — From Benny Greb's *Effective Practice Method* book: three foundational questions every musician answers — **Who am I?** (musical identity and current abilities), **Why am I practicing?** (motivations and goals), and **What improvements am I targeting?** (specific growth areas). These three lists structurally map to the Skill Wheel Onboarding's self-assessment baseline, goal suggestion, and characteristic extraction respectively.
- **Car tire metaphor** — Benny Greb's analogy for the skill wheel: musicianship is like a car tire — if one slice is underinflated (a weak dimension), the whole tire (the musician) can't perform smoothly. Directly informs the weakest-slice focus strategy in onboarding Stage 4 and the radar chart visualization.
- **Peeling the onion** — Benny Greb's term for characteristic-anchored self-assessment: instead of rating an abstract skill, the musician peels through layers of increasingly specific behavioral descriptions until they find the one that matches. This is the model behind the characteristic bands in the onboarding dimension screens.

- **Independent categorical rating** — A chart model where each dimension is assessed on its own scale and displayed independently (e.g., stacked horizontal bars). Contrasts with a **relational profile** model (e.g., radar/spider chart) where the visual encoding implies interplay between dimensions. The Skill Wheel uses independent categorical ratings because each characteristic is scored separately on a 1–10 band with no computed relationship between them.


**Correction (2025-07-18):** The "Independent categorical rating" entry above was written to support the stacked-horizontal-bar model, which has been reversed. The Skill Wheel uses a **radar/spider chart** — see the reversal entry in [Decisions](./decisions.md). The radar chart's concentric rings (mapped to the 1–10 band color zones: red 1–3, amber 4–6, lime 7–8, green 9–10) and polygon overlay remain the authoritative visual encoding.

**Update (2026-05-13):** The "Independent categorical rating" entry above and its correction (which supported stacked bars then restored the radar chart) are both superseded. The authoritative Skill Wheel visualization is a **polar bar / rose chart**: 6 equal 60° wedges, radial distance = score (1–10, max radius 140), 4° gaps between wedges, no connecting polygon. Each wedge reads independently — no implied correlation between characteristics. 5 concentric reference rings at r=14, 42, 84, 112, 140 map to scale bands 1, 3, 6, 8, 10. See the [2026-05-13 decision](./decisions.md).

- **Polar bar / rose chart** — The Skill Wheel visualization geometry: 6 equal 60° wedges around a center point (180, 180), each wedge's radial distance from center represents that characteristic's 1–10 score (max radius 140 = score 10). Wedges are separated by 4° gaps so each reads independently; there is no connecting polygon between wedges. 5 concentric reference rings at r=14, 42, 84, 112, 140 correspond to scale bands 1, 3, 6, 8, 10. Used in onboarding confirmation, Progress tab, and cycle review — only the date stamp and CTA label vary between placements.

- **Fixed 4-band rubric** — The self-rating band descriptions used in onboarding Stage 4: Beginner (1–3), Intermediate (4–6), Advanced (7–8), Expert (9–10). The same four band descriptions appear for every user-defined characteristic — only the characteristic name changes. Replaces the originally-planned per-characteristic name-keyed lookup (which was unbuildable because characteristic names are free-form text). Preserves characteristic-anchored self-assessment (match yourself to a description, not a bare number) while being buildable as ~4 string constants. See the [2026-05-14 decision](./decisions.md).


**Correction (2026-05-14 — REVERSAL):** The "Fixed 4-band rubric" entry above has been superseded. After reviewing Benny Greb's *Effective Practicing for Musicians*, the book contains **no behavioural bands at all**. The authoritative self-rating mechanism is **"visualize your 10"** — the user visualizes what a 10 means for their characteristic guided by four characteristic-agnostic prompts (What would you be able to do at a 10? What elements are included? Why aren't you already at 10? What's the max?), then rates by gut in ~10 seconds. The four prompts are static copy constants in the feature layer — no domain module for rating bands. The rating scale is **0–10** (not 1–10), matching the book and chart axes. See the [2026-05-14 reversal decision](./decisions.md).

- **nanoid** — A tiny, fast unique ID generator. Used for characteristic IDs in the app. The project imports from the `nanoid/non-secure` entry point (not the default `nanoid`) because React Native's Hermes runtime lacks `crypto.getRandomValues`; the non-secure variant uses `Math.random()` instead. Sufficient for locally-unique IDs where cryptographic collision resistance is not required.
- **nanoid/non-secure** — The `nanoid` variant that uses `Math.random()` for ID generation instead of `crypto.getRandomValues`. Required for React Native / Hermes compatibility. See [Test Harness & Dependency Setup](./learnings/test-harness-setup.md).
- **transformIgnorePatterns** — A Jest configuration option that controls which `node_modules` packages are transformed by Babel. The default `jest-expo` preset excludes all `node_modules`, but ESM-only packages (like `nanoid`) must be exempted or Jest fails with a syntax error on `export` statements. See the [2026-05-14 test harness decision](./decisions.md).

- **Characteristic** — A domain type (`src/domain/onboarding/types.ts`) representing a user-defined skill dimension. Fields: `id` (stable nanoid; survives rename/reorder), `name` (free-form, user-entered), `order` (1-indexed user-defined order; tiebreaker for ranking), `score` (optional integer 0–10; undefined until rated in Stage 4 of onboarding).
- **ThreeLists** — A domain type (`src/domain/onboarding/types.ts`) representing the user's Three Lists exercise output. Fields: `who` (5–10 names, order preserved), `why` (who-name → quality strings, keyed by name not id), `improvements` (min 3 strings).
- **Baseline** — A domain type (`src/domain/onboarding/types.ts`) representing a persisted onboarding snapshot. Fields: `version` (schema version, currently 1), `characteristics` (all scored — `score` defined for every entry in practice), `focusAreas` (0–2 characteristic IDs), `createdAt` (ISO-8601), `userId` (`"local"` sentinel in V1; no auth/cloud yet).
- **domain/onboarding/** — The domain subdirectory for shared onboarding types (`src/domain/onboarding/types.ts`). Placed in `domain/` (not a feature folder) because multiple consumers — the onboarding store + stage screens, the SkillWheelChart component (`src/shared/components`), and future Progress/Cycle-Review features — all consume `Characteristic`, and none may import another feature.

- **baselineRepository** — The domain-shaped persistence API at `src/features/onboarding/data/baselineRepository.ts`. Exposes `completeOnboarding(baseline)`, `getBaseline()`, `isOnboardingComplete()`, and `clear()`. Uses versioned, namespaced AsyncStorage keys. Writes baseline first, then the completion flag — so a crash between writes degrades to "restart onboarding" rather than a corrupt half-state. Defensive read: both flag AND readable baseline must be present to consider onboarding complete.
- **Versioned keys** — The AsyncStorage key naming convention `epm.{domain}.v{version}` (e.g., `epm.baseline.v1`, `epm.onboardingComplete.v1`). Namespaced under `epm.` so future schema bumps or a SQLite migration can coexist and migrate. The `v1` suffix is explicit so a v2 schema can live alongside v1 during migration.
- **storage.ts** — The thin typed AsyncStorage wrapper at `src/shared/lib/storage.ts`. Exports `getJson<T>(key): Promise<T | null>`, `setJson<T>(key, value): Promise<void>`, and `remove(key): Promise<void>`. Swallows JSON parse errors (logs warning, returns null). Keeps the `@react-native-async-storage/async-storage` import in one file so feature code and tests never import AsyncStorage directly — the wrapper is mockable.
- **Atomic-ish write** — The persistence pattern where the baseline JSON snapshot is written first, then the `onboardingComplete` flag. AsyncStorage has no multi-key transaction, so this is not truly atomic. But the read side treats "flag true but baseline missing/corrupt" as NOT complete (defensive), so a crash between the two writes degrades to "restart onboarding" rather than producing a corrupt half-state. The reverse order (flag first, then baseline) was rejected because a crash after the flag write would make the app think onboarding is complete with no data.

- **palette.ts** — The colour assignment module at `src/shared/components/skill-wheel/palette.ts`. Exports `colourForIndex(i)` which returns a deterministic wedge colour by array index, cycling mod 6. Computed at render time, not stored with characteristic data — the same characteristic always gets the same colour based on its position in the array. Separated from the chart component so the colour assignment rule is explicit and testable in isolation.

- **OnboardingState** — A domain type (`src/domain/onboarding/types.ts`) representing the full in-memory onboarding state consumed by `canAdvance`. Includes `threeLists` (the Three Lists exercise output), `characteristics` (array of user-defined characteristics with optional scores), and other stage-specific fields. Zero-dependency — pure TypeScript interface, no React/RN.
- **canAdvance** — The single forward-navigation gate function at `src/domain/onboarding/guards.ts`. Signature: `canAdvance(stage: Stage, s: OnboardingState): boolean`. Called by the onboarding store before `next()`. Self-gating stages (intro, confirm, focus, complete) always return true. Gated stages enforce domain rules: `threeLists` requires complete lists (5–10 who, every who has ≥1 why, ≥3 improvements), `characteristics` requires ≥3 characteristics, `rating` requires all characteristics scored. Screens never re-implement gating — the "Next" button binds `disabled` to `!canAdvance(currentStage, storeState)`.
- **threeListsComplete** — A standalone pure domain function at `src/domain/onboarding/guards.ts`. Signature: `threeListsComplete(lists: ThreeLists): boolean`. Validates: who count 5–10, every who entry has ≥1 why string, improvements ≥3. Used by `canAdvance` for the `threeLists` stage gate. Separately exported so it can be unit-tested in isolation.
- **stages.ts** — The stage machine definition at `src/domain/onboarding/stages.ts`. Exports `STAGES` (a `const` array of the 7 stage identifiers: `intro`, `threeLists`, `characteristics`, `rating`, `confirm`, `focus`, `complete`) and the derived `Stage` type. Implements the Orchestration FR2 table. Zero-dependency.
- **guards.ts** — The navigation guard module at `src/domain/onboarding/guards.ts`. Exports `canAdvance` and `threeListsComplete` as pure domain functions. Implements forward-navigation gating per the feature spec: the store calls `canAdvance` before advancing; screens never re-implement gating logic.

- **ratingPrompts** — The four static, characteristic-agnostic "visualize your 10" prompts at `src/features/onboarding/stages/ratingPrompts.ts`: (1) What would you be able to do at a 10? (2) What elements are included? (3) Why aren't you already at 10? (4) What's the max? Sourced directly from Benny Greb's *Effective Practicing for Musicians*. Same four prompts appear for every characteristic — only the characteristic name changes. Feature-layer static copy constants, not domain logic.
- **Midpoint nudge** — The self-rating rule (Rule 1: Avoid 5) implemented as an inline prompt on the RatingScreen. When the user selects 5 (the arithmetic midpoint of the 0–10 scale), two tappable override options appear: "I can do this sometimes" → sets score to 4, "I can usually do this" → sets score to 6. A "Keep 5" option dismisses the nudge and preserves the midpoint. Pure UI/store interaction — no domain function. Discourages the low-signal midpoint to produce a wheel with real shape.
- **SCALE_MIN / SCALE_MAX** — Constants defined in the RatingScreen (`src/features/onboarding/stages/RatingScreen.tsx`) that control the self-rating scale range. Currently set to 0 and 10 (0–10 scale, matching Benny Greb's book and the chart axes). Defined as single constants so the scale can flip with a one-line edit when product confirms the final range.


- **detectFlatWheel** — A pure domain function at `src/domain/onboarding/wheel.ts`. Signature: `detectFlatWheel(characteristics: Characteristic[]): { isFlat: boolean, range: number }`. Computes `max(scores) - min(scores)` with `threshold = 2`. If the range is ≤2, the wheel is considered "flat" — all scores are too close together, suggesting the user may have avoided making real distinctions. Shared by onboarding Stage 5 (ConfirmationScreen flat-wheel nudge), Stage 6 (tip selection), and the ranking module for Focus Selection. Pure, zero-dependency, testable with plain Jest.
- **Flat-wheel nudge** — A UI intervention on the ConfirmationScreen (Stage 5) triggered when `detectFlatWheel` returns `isFlat: true`. Displays copy: "Your scores are very close together. Every musician has relative strengths and weaknesses. Would you like to review your ratings?" with two buttons: "Review ratings" → `store.back()` (returns to Stage 4) and "Proceed anyway" → `store.next()` (advances to Stage 6). Implements the "differentiation warning" from the self-rating rules — a flat wheel has no meaningful shape and produces weak focus-area suggestions.


- **FocusSelectionScreen (Stage 6)** — The onboarding stage at `src/features/onboarding/stages/FocusSelectionScreen.tsx` where the user reviews a ranked list of their characteristics and chooses 0–2 focus areas (or skips). Renders each characteristic with name, "X / 10" score, and a selection affordance. Includes a passive tip whose content is selected by wheel shape (flat, large gap, or default). Tap-to-toggle selection capped at 2 with inline feedback on third tap. Continue/Skip both call `store.setFocusAreas()` then `store.next()`. State is store-backed so back-navigation from Stage 7 preserves selections. Explicitly not a recommendation engine — the user knows their priorities better than an algorithm.
- **rankCharacteristics** — A pure domain function at `src/domain/onboarding/ranking.ts`. Signature: `rankCharacteristics(characteristics: Characteristic[]): Characteristic[]`. Sorts by (score ASC, order ASC). Used by Stage 6 (FocusSelectionScreen) to display the ranked list. Pure, zero-dependency, unit-tested.
- **pickWeakestSlices** — A pure domain function at `src/domain/onboarding/ranking.ts`. Signature: `pickWeakestSlices(characteristics: Characteristic[], count?: number): Characteristic[]`. Returns the lowest N characteristics by score, tiebreaking by order. Built now as a domain utility for future Cycle Review; not used by the Stage 6 UI (which shows all characteristics ranked, not just the weakest). Pure, zero-dependency, unit-tested.
- **Passive tip (Stage 6)** — Small, unobtrusive hint text on the FocusSelectionScreen styled like a loading-screen hint. Content is selected by wheel shape using a most-specific-wins cascade: if `detectFlatWheel().isFlat` → flat-wheel tip; else if range ≥ 5 → large-gap tip; else → default tip. The tips encourage the user without pushing a specific choice — the screen surfaces the ranked list and gets out of the way.
- **Cap-2 selection** — The Stage 6 selection mechanic: tapping a characteristic toggles it, but a third tap (when 2 are already selected) shows inline feedback and does not change the selection. The counter reads "N of 2 selected." Continue is always enabled (0, 1, or 2 selected), where 0 is equivalent to Skip.
- **ranking.ts** — The domain module at `src/domain/onboarding/ranking.ts` containing `rankCharacteristics` and `pickWeakestSlices`. Both are pure, zero-dependency functions. Shared with Stage 6 and future Cycle Review. `rankCharacteristics` also consumes `detectFlatWheel` from `src/domain/onboarding/wheel.ts`.

- **useBaseline** — A React hook at `src/features/onboarding/useBaseline.ts` that serves as the single seam for baseline-dependent features. Returns `{ baseline: Baseline | null, loading: boolean, isComplete: boolean }`. Uses `useFocusEffect` from expo-router to re-read `baselineRepository.getBaseline()` and `baselineRepository.isOnboardingComplete()` on mount and every tab focus — so the wheel appears immediately after completing onboarding. Defensive gating: if `isComplete` is true but `baseline` is null (corrupt state — flag set, baseline missing), treats as NOT complete. Any future feature that depends on a baseline (e.g., Cycle Review delta computation) imports this hook and checks `baseline === null` before computing — either prompts onboarding or degrades gracefully (FR6.3).
